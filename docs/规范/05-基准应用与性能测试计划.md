# Aster 基准应用与性能测试计划

**文档编号：** ASTER-BENCH-001
**版本：** V0.1 Draft
**状态：** 草案。测量方法待 EXP-001 实际运行后修订。
**依赖：** 基础设计文档 §5.3、ASTER-ARCH-001 §17、02 UI 规范

---

## 1. 目的

本计划回答三个问题：

1. Aster 的原型在体积、内存、启动时间、编译时间上处于什么水平？
2. 相同功能下，与 Electron、Tauri、Qt、Slint 相比差距在哪里？
3. 哪些"目标数字"（5 MB、30 MB、300 ms、200 ms）能被实测支持，哪些必须修改？

**核心原则：** 没有基线数据之前，不对外承诺任何性能数字。所有比较必须使用相同功能、相同平台、相同资源和相同测量方法（基础设计文档 §5.3，设计讨论中的对比原则）。

## 2. 基准应用

### 2.1 三个基准应用

| 编号 | 应用 | 目的 | 覆盖的能力 |
|---|---|---|---|
| B1 | 最小应用（Hello + 按钮 + 计数器） | 测量运行时的固定成本 | 窗口、按钮、文本、单个状态 |
| B2 | 表单工具 | 测量常规输入界面的成本 | 输入框、校验、中文输入、保存、Row/Column 布局 |
| B3 | 文件管理器（模拟数据） | 测量复杂列表与布局 | 侧栏、搜索、列表（1000+ 行）、详情面板、主题切换 |

数据分析工作台是设计讨论中选定的第三类基准应用，但实现推迟到 V0.2 之后，不属于 V0.1 的门禁。

### 2.2 与 EXP 实验的对应

| 基准 | 对应实验 | 对照对象 |
|---|---|---|
| B1 | EXP-001 原生应用基准 | Aster 原型、Slint、Tauri、Electron、Qt（可选） |
| B2 | EXP-003 对照实验（Aster 自有语义 vs Slint） | Slint |
| B3 | EXP-002 复杂布局验证、UI Spike 文件管理器 | Slint（同需求）、Aster 原型 |

### 2.3 功能一致性要求

每个对照实现必须满足同一份功能清单（写在各基准应用目录的 `SPEC.md` 中）。清单未覆盖的功能不得被计入其他框架的"更轻"。

- 不允许用 Aster 的空窗口与其他框架的完整应用比较。
- 若某框架无法实现某一功能，记录为"未实现"，而不是忽略。
- 每个实现的代码行数、依赖数量、开发时间（小时，由同一人记录）单独记录，作为开发成本指标。

## 3. 测量指标

| 指标 | 定义 | 单位 |
|---|---|---|
| 安装包体积 | 平台发行包的文件大小（压缩前与压缩后各记录一次） | MB |
| 运行时依赖 | 动态链接库列表，以及系统 WebView 或运行时要求 | 列表 |
| 空闲内存 | 窗口显示后 30 秒的 RSS / 工作集 | MB |
| 峰值内存 | 基准操作期间的最大 RSS | MB |
| 冷启动时间 | 进程启动到首帧可见 | ms |
| 热启动时间 | 同一会话内第二次启动到首帧可见 | ms |
| 全量编译时间 | 清理缓存后的构建 | s |
| 增量编译时间 | 修改一个文件（布局属性）后的构建 | s |
| 界面响应时间 | 点击按钮或输入一个字符到界面刷新 | ms |
| 大列表滚动帧时间 | 1000 行列表滚动期间的帧时间分布 | ms（p50、p95、p99） |
| 布局计算时间 | 窗口缩放一次的布局耗时 | ms |
| 热更新时间 | 修改样式后刷新 | ms（仅 Aster 原型，V0.2 之后有意义） |

## 4. 测量方法

### 4.1 环境记录

每次测量必须记录：

- 硬件型号、CPU、内存、存储类型；
- 操作系统版本与构建号；
- 显示器分辨率、缩放比例、刷新率；
- 工具链版本（Rust、LLVM 或后端、各对照框架）；
- 构建模式（release，优化级别、LTO 设置、strip 设置）；
- 电源状态（插电）、后台负载（测量前关闭非必要进程）。

所有测量数据与环境记录保存在 `benchmarks/results/<日期>-<平台>-<实现>.json`。

### 4.2 重复与统计

- 启动、内存与编译类指标：每个配置至少运行 **10 次**，报告中位数、最小值、最大值。
- 帧时间：每个场景至少 **3 次完整滚动**，报告分位数。
- 不得只报告最好的一次。失败的运行必须保留并说明。
- 每次测量前进行预热（一次空运行），预热结果不计入。

### 4.3 工具

| 指标 | 工具（候选） |
|---|---|
| 体积 | 文件系统统计、`strip` 前后对比 |
| 内存 | 平台原生工具（macOS `footprint`/`vmmap`，Linux `/proc/<pid>/status`，Windows 性能计数器） |
| 启动时间 | 启动时间戳（进程创建到首帧 present 的回调）与录屏辅助 |
| 帧时间 | 平台帧统计 API，或由渲染后端记录的 present 时间戳 |
| 编译时间 | `time` 命令与构建系统的时间统计 |

具体工具在 EXP-001 中确定。所选工具必须对所有对照实现一致。

### 4.4 构建模式

- 所有对比使用 **release 模式**，并分别记录"默认配置"与"优化配置"（如 LTO、strip、符号裁剪）。
- 不允许只对 Aster 启用优化、对对照框架使用默认配置。
- 对照框架的优化选项必须按其官方发布文档中的推荐设置。

## 5. 目标数字的处理

基础设计文档与设计讨论给出了以下探索目标。本计划的规定如下：

| 探索目标 | 处理方式 |
|---|---|
| 最简应用安装包 < 5 MB | 作为 B1 的探索目标。按平台分别测量。**测量前不作为承诺。** |
| 普通表单工具冷启动 < 300 ms | 作为 B2 的探索目标。定义启动为"进程创建到首帧可见"，以便与其他框架比较。 |
| 闲置内存 < 30 MB | 作为 B1 的探索目标。该数字必须区分进程与系统级指标。 |
| 热更新 < 200 ms | 作为 V0.2 的探索目标，只对 Aster 原型测量。 |

**修订规则：** EXP-001 完成后，项目维护者根据实际数据修订上述数字，并在 ADR 中记录修订理由。修订可以更宽松，也可以更严格，但必须基于同场测量。

## 6. 测量流程

```
1. 准备：确认环境记录模板、功能清单（SPEC.md）与对照实现版本。
2. 构建：按 §4.4 分别构建各实现，记录构建时间与产物。
3. 预热：运行一次，丢弃结果。
4. 测量：按 §4.2 重复运行，保存原始数据。
5. 功能验证：执行 SPEC.md 中的功能清单，确认每个实现都完成相同功能。
6. 汇总：计算统计量，生成对比表。
7. 复核：另一人复现至少一个指标（如冷启动）。
8. 归档：保存数据、环境记录与构建脚本。
```

第 5 步不通过的实现，其性能数据不得进入对比表。

## 7. 回归基准

- 每次合并到主分支前，CI 运行 B1 的体积与编译时间检查（同一 CI 机器上的相对比较）。
- 相对于上一个基线的回归超过 **10%**（体积、内存、启动时间），CI 标记为警告；超过 **20%**，需要维护者审查后才能合并。
- 回归阈值只用于发现问题，不代表性能承诺。
- 回归基线在每个里程碑更新，并记录更新原因。

CI 机器与开发机器的数据不得混合比较。

## 8. 排除与限制

- 不测量开发模式（含调试信息与热更新服务）的体积，发行体积只看发行构建。
- 不以单一空窗口证明运行时很轻。B2 与 B3 必须与 B1 一起报告。
- 系统 WebView（Tauri）与 Electron 的运行时体积以"需要用户机器上已有的组件"与"随应用分发的组件"两种口径分别报告。
- 不对外宣传未经同场测量的数字。

## 9. 与开发阶段的关系

| 阶段 | 基准工作 |
|---|---|
| Phase 0（当前） | 制定本计划；完成 EXP-001 的环境与 B1 实现 |
| UI Spike 期间 | 对 B3（文件管理器）做 Slint 与 Aster 原型对比（EXP-003） |
| Phase 1 | 语言原型的编译时间与增量编译时间基线 |
| Phase 2 | B2 与 B3 的完整测量；布局计算时间 |
| Phase 3 | 热更新与布局检查开销 |
| Phase 6 | 全平台发布测量、与 Electron/Tauri/Qt 完整对比 |

## 10. 输出物

- `benchmarks/apps/B1-minimal/`、`B2-form/`、`B3-file-manager/`：应用源码与各自 `SPEC.md`。
- `benchmarks/results/`：原始数据与环境记录。
- `benchmarks/reports/`：对比报告（每次正式测量一份，包含方法、数据、结论与局限）。
- 报告必须说明：哪些数字来自实测，哪些是推断，哪些功能未实现。

## 11. 验收条件（对应 EXP-001）

EXP-001 通过的条件（ARCH-001 §17）：**能够建立可重复的基准构建流程，记录真实数据与构建配置。**

具体包括：

1. B1 能在至少两个平台上从干净环境构建；
2. 同一构建脚本重复运行得到的体积完全一致（发行构建的确定性，见 04 §8）；
3. 每个指标的重复测量数据保存，并能复现报告中的中位数；
4. 报告包含环境记录与构建配置。

EXP-003 通过的条件：得到可重复的对照记录，明确 Slint 可直接复用的能力与必须自研的部分。
