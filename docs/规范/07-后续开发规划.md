# Aster 后续开发规划

**文档编号：** ASTER-PLAN-001
**版本：** V0.1 Draft
**状态：** 草案。阶段切换由门禁决定，不由日历决定（设计讨论 §四）。
**依赖：** 基础设计文档 §六（决策规则）、§七（交付物）；ASTER-ARCH-001 §17–§19；技术验证阶段.md；00–06 全部规范

---

## 1. 规划原则

1. **门禁驱动。** 每个阶段有明确的入口与出口条件。条件未满足时不进入下一阶段，即使日历已到。
2. **先验证假设，再扩展。** 高风险实验（EXP-001、003、005）优先，编译器与 UI 的大规模功能在其之后。
3. **最小闭环优先。** 一个能创建、编译、运行、检查、修改的应用，优先于任何单个模块的完整实现。
4. **文档与实现同步。** 规范变更与代码变更在同一 PR 或紧邻 PR 中完成。
5. **周期只是估计。** 设计讨论给出的 12 个月路线为建议，按一名有经验的系统工程师配合 AI 工具估算。业余推进时周期会明显变长。本规划不做时间承诺，只定义顺序与门禁。

## 3.1 平台里程碑（ADR-016）

在 G0（桌面端）通过之后，按以下顺序推进移动端，不得跳过：

| 里程碑 | 内容 | 出口条件 |
|---|---|---|
| M-A Android 原型 | 用共享 UI 模型与业务核心构建最小 Android 应用；在模拟器或真机运行；触摸与生命周期映射到共享事件 | 构建产物可安装运行；布局检查结果与桌面版一致；记录能力声明与未支持项 |
| M-I iOS 构建与运行 | 完整 Xcode 与签名环境下构建并运行同一原型 | 构建与运行记录；未支持能力的诊断可复现 |

当前环境不满足 M-I 的前置条件（只有 Command Line Tools；Android SDK 与 NDK 未安装），因此这两个里程碑在环境准备完成之前保持未开始。

## 4. 阶段详情

### 4.1 P0：设计冻结与验证准备

**目标：** 决定"能不能开始写编译器"所需的最少信息，并启动最关键的两个实验。

**工作项：**

| 编号 | 工作 | 依据 |
|---|---|---|
| P0-1 | 完成本套规范的评审与修订（见 00 §6 冲突处理） | 基础设计文档 §七 |
| P0-2 | 把 ADR-001 至 012 迁移到 `docs/adr/`，更新状态 | 06 §6.2 |
| P0-3 | 建立仓库骨架（只含 06 §1.1 中 P0 需要的目录），并加入中文字符 CI 检查 | 06 §1、§3.0 |
| P0-4 | 启动 **UI Spike 01**：原型 A（Slint 基线）与原型 B（Aster UI 模型，输出到 Slint） | 技术验证阶段.md |
| P0-5 | 完成 **EXP-001**：B1 最小应用在至少一个平台上可重复构建，采集首轮数据 | 05 §11 |
| P0-6 | 决定 **Q-01**（内存模型）的临时方案，或设定截止时间与决定责任人 | 01 §14、00 §5 |
| P0-7 | 确定首个目标平台与最低系统版本（ARCH-001 ADR-012） | ARCH-001 §15 |
| P0-8 | 确定许可证（Apache-2.0 或 MIT）与 DCO/CLA 方案 | 06 §8 |

**UI Spike 的验证问题**（来自技术验证阶段.md）：

> 我们能不能在不依赖完整浏览器引擎的前提下，构建现代、轻量、跨平台的桌面界面，并让 AI 通过结构化数据准确检查和修改布局？

Spike 完成的标准：技术验证阶段.md §四 的五个实验全部有记录（通过或失败均可，失败需要说明原因）。

**门禁 G0（进入 P1 的条件）：**

- [ ] 本套规范经过至少一次完整评审，所有 "待验证" 项都有责任人与时限；
- [ ] Q-01（内存模型）有临时方案，或已记录为"P1 期间不影响前端"的决定；
- [ ] UI Spike 01 的五个实验至少完成四个，并且形成书面结论；
- [ ] EXP-001 的 B1 在至少一个平台上有可重复的构建记录；
- [ ] 确定"Aster UI 语义层"与"渲染后端"的边界，且 Spike 结论不推翻该边界；
- [ ] 仓库可以在干净环境中执行 `cargo test`（即使测试数量为零）。

> 注：基础设计文档要求"关键架构决策明确、技术风险有验证方案后，才进入编译器原型开发"。G0 因此要求的是**决定与方案**，而不要求所有实验结束。对于仍未验证的部分，P1 的设计必须保持可替换（例如后端通过接口隔离）。

#### 4.1.1 P0 与 P1 的并行

以下工作可以在 G0 之前开始，因为它们不依赖 UI 决策：

- `aster-syntax`（词法与语法，L0–L1）的实现；
- `aster-diag`（诊断结构与错误码表）；
- 01 语言规范中的正反例测试用例编写。

这些工作不得在 G0 之前合并到 `main` 中依赖 UI 的 API。

### 4.2 P1：语言原型

**目标：** 证明语言设计能够被编译、诊断和执行，覆盖 01 规范中的 V0.1 子集。

**工作项（建议顺序）：**

1. `aster-syntax`：无损 CST、词法、语法（01 §2–§7）；
2. `aster-diag`：结构化诊断（03 §4）、错误码表与 JSON 输出；
3. `aster-cli`：`aster check`、`aster fmt`（唯一格式化器，01 §15）；
4. `aster-sema`：名称解析、类型检查（01 §3–§5）、状态写入检查（01 §8）、`match` 穷尽性（01 §6）；
5. 解释执行器或最小代码生成（用于验证语义；正式后端由 EXP-006 决定）；
6. `aster-cli`：`aster build`、`aster run`（B1 的纯逻辑部分，不含 UI）；
7. 错误码的正反例测试（01 §17）。

**EXP-006（代码生成后端对比）** 在 P1 中期进行。对比对象至少包括 LLVM 与一个轻量替代方案。P1 的后端接口必须与具体后端解耦。

**内存模型（Q-01）** 在 P1 中期必须有决定。若 EXP-001 显示引用计数的开销不可接受，可修订 01 §14 并通过 ADR 记录。

**门禁 G1（进入 P2 的条件）：**

- [ ] 01 规范中 V0.1 的全部语法与语义规则都有正例与反例测试；
- [ ] 错误码表中每个码都有至少一个反例测试，且检查码与源位置；
- [ ] 同一源码连续两次构建的产物哈希一致（确定性）；
- [ ] 诊断输出通过 03 §4 的 JSON 格式测试；
- [ ] EXP-006 有书面结论，选定首选后端，或明确"P2 期间继续使用解释执行"；
- [ ] Q-01 已决定，并在 01 §14 中标记为冻结或修订；
- [ ] `aster fmt --check` 在 CI 中通过，且对 `examples/` 的格式化结果稳定（幂等）。

### 4.3 P2：原生 GUI 核心

**目标：** 让语言具备完整桌面程序的表达能力，并在真实应用上验证 02 规范。

**工作项：**

1. `aster-ir`（L3）：组件树、绑定、事件、样式来源；
2. `aster-layout`（L4）：测量与排布（02 §5），布局冲突诊断；
3. `aster-render-ir`（L5 数据结构）与渲染后端接口（02 §11）；
4. `aster-backend-slint`（临时）或正式后端：显示列表的绘制；
5. `aster-runtime`：状态、动作、异步任务与取消（01 §8–§10，02 §8）；
6. `aster-platform`：窗口、输入、焦点、DPI、文件对话框（第一平台）；
7. 15 个 V0.1 组件（02 §12.1）；
8. 文字与输入法（02 §9）；
8a. 本地化语言包：加载、回退链、运行时切换、伪本地化布局测试（02 §9.1）；
9. 文件管理器基准 B3 运行（模拟数据）。

**EXP-002（复杂布局）** 与 **EXP-005（中文与输入法）** 在本阶段完成。EXP-005 的失败会阻塞 P2 出口，因为中文输入是产品的基本要求，不是后期功能。

**门禁 G2（进入 P3 的条件）：**

- [ ] B3 在至少两个平台上运行，功能清单（B3 的 SPEC.md）全部实现；
- [ ] EXP-005 通过：中文输入、候选窗口定位、组合文本、删除、光标、复制粘贴、字体回退在目标平台上完成基本流程；
- [ ] 文件管理器在 `en` 与 `zh-CN` 之间切换后界面正确更新，且伪本地化运行无布局错误（02 §9.1）；
- [ ] EXP-002 的布局错误（溢出、冲突、重叠）可被自动检测，并给出可追踪原因；
- [ ] 布局快照测试覆盖至少 3 个窗口尺寸与 2 个 DPI；
- [ ] `List` 的虚拟化结果与全量布局一致（02 §12.3）；
- [ ] 第一个平台的 B1、B2、B3 数据已记录（05 §11）。

### 4.4 P3：AI 开发闭环

**目标：** 让 AI 能够观察程序、修改程序并验证结果，实现 03 规范中的闭环。

**工作项：**

1. `aster-protocol`：JSON-RPC 服务、`inspect.*`、`diagnose`、`patch.dry_run` / `patch.apply`（03 §6、§8）；
2. 运行时的状态快照与事件时间线；
3. 布局检查的 `size_sources` 输出（03 §8.3）；
4. 补丁的回滚保护（03 §6.3）；
5. `aster diff`、`aster impact`（03 §7）；
6. 增量构建（只重新检查受影响的节点）；
7. 诊断包导出（03 §5.2）；
8. 布局快照测试的更新流程（人工审查）。

**EXP-004（AI 自动修复闭环）** 在本阶段执行。设计一组包含布局错误、类型错误、状态错误和事件处理错误的任务，分别记录成功率、修复次数、耗时与回归缺陷。

**门禁 G3（进入 P4 的条件）：**

- [ ] EXP-004 的结果已记录，包括失败案例；
- [ ] 补丁的基线检查与回滚有测试覆盖；
- [ ] `inspect.layout` 对相同输入输出逐字节相同（03 §12）；
- [ ] AI 能完成至少一次"修改布局 → 运行 → 读取诊断 → 修复 → 测试通过"的完整流程，并记录过程；
- [ ] AI 无法修改快照期望值与权限清单（有测试证明）。

**风险提示：** 若 EXP-004 的成功率低于预期，应优先改进诊断内容与建议质量，而不是放宽验收标准（设计讨论硬规则 5）。

### 4.5 P4：设计系统

**目标：** 生成的应用具有可接受的视觉质量，主题切换只修改令牌。

**工作项：**

1. `design` 块与令牌类型检查（02 §6.1）；
2. 浅色与深色主题、系统主题跟随（02 §6.4）；
3. 命名样式与 `style_source` 查询（02 §6.3）；
4. 属性过渡动画（02 §6.5）；
5. 对比度检查（02 §10，`W4400`）；
6. 视觉回归测试（截图比较作为辅助；布局断言仍是主要依据）。

**门禁 G4：**

- [ ] 主题切换不修改组件结构（有测试证明）；
- [ ] 令牌未定义与类型不匹配都能被诊断；
- [ ] 对比度检查在 B2、B3 上运行，且结果被记录；
- [ ] 过渡动画不改变布局结果。

### 4.6 P5：扩展生态

**目标：** 第三方能够独立开发、测试、发布组件包，且权限与信任边界清晰。

**工作项：**

1. 包管理器：清单、锁文件、哈希校验、离线缓存（04 §5–§6）；
2. 许可证与漏洞检查（04 §7）；
3. A 类（编译期库）完整流程；
4. B 类（原生扩展）：C ABI、版本协商、授权加载（04 §3.2）；
5. C 类（隔离插件）：独立进程、IPC、资源限制（04 §3.3）；
6. 权限审计命令（04 §2.3）；
7. 示例组件包与示例业务库（EXP-008）；
8. 第三方文档规范（组件元数据导出，02 §3.3）。

**EXP-007（插件安全原型）**：一个普通库与一个隔离插件，测试权限限制、异常退出、版本不匹配与依赖升级。

**EXP-008（第三方组件开发流程）**：由独立示例项目开发组件包，完成构建、测试、版本锁定与发布，**不修改编译器源码**。

**门禁 G5：**

- [ ] EXP-007 结果已记录，明确哪些故障被隔离、哪些能力依赖操作系统或可信沙箱（Q-05 有结论）；
- [ ] EXP-008 完成，且过程中未修改编译器源码；
- [ ] 篡改依赖内容时构建失败（有测试）；
- [ ] 未声明权限的调用被拒绝（有测试）；
- [ ] 锁文件在干净环境中可以复现构建。

### 4.7 P6：跨平台 Beta

**目标：** 三个平台达到一致的功能测试结果，并可供外部开发者试用。

**工作项：**

1. Windows、macOS、Linux 的完整平台后端（窗口、菜单、对话框、剪贴板、托盘、通知、快捷键）；
2. 三平台的输入法、字体回退、DPI 与显示器变化；
3. CI 矩阵（三平台 × 发行与调试构建）；
4. 发布签名与可复现构建验证（04 §8）；
5. 安全审计与依赖审计；
6. 三个基准应用的端到端验证；
7. 完整的对比报告（Electron、Tauri、Qt、Slint，05 §2.3）；
8. 文档：语言参考、组件参考、入门教程、示例工程。

**门禁 G6：**

- [ ] 同一业务代码在三个平台通过相同的功能测试（设计讨论 V0.4 验收）；
- [ ] 基准报告包含同场对比数据，且报告说明了未实现的功能与局限；
- [ ] 安全审计的高危问题已修复或有明确接受记录；
- [ ] 发行产物签名并可验证；
- [ ] 外部开发者能按文档完成一个示例应用（记录其反馈）。

### 4.8 P7：稳定版准备

**目标：** 冻结核心语法与公共 API，发布 1.0 候选。

**工作项：**

1. 冻结 01 规范与标准库公共 API；
2. 迁移工具与兼容性测试；
3. 修复 Beta 期间的关键问题；
4. 语言规范与标准库参考的完整发布；
5. 安全政策、维护者流程、长期支持计划；
6. 验证可复现构建与签名流程。

**门禁 G7（1.0 发布条件）：**

- [ ] 上一个 Beta 周期中没有未解决的 P0 级缺陷；
- [ ] 兼容性测试覆盖所有已发布语法；
- [ ] 维护者人数满足 06 §5.3 的双人评审要求；
- [ ] 基础设计文档 §5 的关键成功标准全部有证据。

## 5. 风险登记

| 编号 | 风险 | 可能性 | 影响 | 缓解 | 触发信号 | 相关实验 |
|---|---|---|---|---|---|---|
| R-01 | 中文输入法与自绘控件的交互不可接受 | 中 | 高 | P0 Spike 起即测试；EXP-005 作为 G2 门禁；必要时对输入控件使用原生控件 | Spike 中输入法候选窗口定位失败 | EXP-005 |
| R-02 | 运行时体积超出预期，轻量定位不成立 | 中 | 高 | 同场基准；早期测量 B1；渲染后端可替换 | B1 体积远超 Slint/Tauri 基线 | EXP-001、EXP-003 |
| R-03 | 自研布局语义带来的复杂度超过收益 | 中 | 高 | UI Spike 对照 Slint；只自研语义与检查，不自研求解器 | Spike B 的功能完成成本显著高于 A | EXP-003 |
| R-04 | AI 闭环在真实任务上成功率低 | 中 | 高 | 先改进诊断与补丁设计；记录失败案例；不放宽验收 | EXP-004 成功率低于 G3 预期 | EXP-004 |
