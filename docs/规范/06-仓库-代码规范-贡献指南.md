# Aster 仓库结构、代码规范与贡献指南

**文档编号：** ASTER-REPO-001
**版本：** V0.1 Draft
**状态：** 草案。
**依赖：** 基础设计文档 §七（仓库规范）、设计讨论（硬规则）、ASTER-ARCH-001 ADR-001/002/012

---

## 1. 仓库形态

采用单仓库（monorepo），编译器、运行时、UI、工具、标准库、示例与测试在同一仓库中版本协调。

**只创建正在开发的模块。** 设计讨论中的完整目录树是长期规划，不是第一天的目录结构。空目录不得提交。

### 1.1 目标目录（按阶段创建）

以下为 V0.1 的目标结构。每个目录在对应阶段（07 文档）开始开发时才创建。

```
aster/
├── README.md
├── LICENSE                 # Apache-2.0（待发布前审查，见 §8）
├── NOTICE
├── CONTRIBUTING.md         # 本文 §2-§7 的简版
├── SECURITY.md             # 漏洞披露流程（见 04 §11）
├── GOVERNANCE.md           # 维护者与决策流程
├── CODEOWNERS
├── Cargo.toml              # Rust workspace 根
├── aster.toml              # 工具链版本与项目级配置（如 toolchain）
├── docs/
│   ├── 设计原始文档/        # 原始讨论记录，只读归档
│   ├── 规范/                # 本套规范（01–07）
│   ├── adr/                 # 架构决策记录（ADR-NNN-标题.md）
│   └── rfcs/                # 语言与公共接口的变更提案
├── crates/
│   ├── aster-syntax/        # 词法、语法、无损 CST（L0–L1）
│   ├── aster-diag/          # 诊断结构、错误码表、JSON 输出
│   ├── aster-sema/          # 名称解析、类型检查（L2）
│   ├── aster-ir/            # UI IR、ID 生成、序列化（L3）
│   ├── aster-layout/        # 布局引擎（L4）
│   ├── aster-render-ir/     # 显示列表定义（L5 的数据结构，不含后端）
│   ├── aster-runtime/       # 运行时核心：状态、动作、任务、事件
│   ├── aster-platform/      # 平台适配（窗口、输入、文件对话框），唯一可用 unsafe 的区域之一
│   ├── aster-backend-slint/ # 临时渲染后端（Spike 与 EXP-003）
│   ├── aster-cli/           # 命令行入口（aster 可执行文件）
│   ├── aster-protocol/      # JSON-RPC 协议服务（03 §8）
│   └── aster-test/          # 测试辅助：布局快照、诊断断言
├── std/                     # 标准库源码（Aster 语言，01 §12）
├── examples/                # 可编译的示例应用（非基准）
├── benchmarks/
│   ├── apps/                # B1–B3（05 §2）
│   ├── results/             # 原始测量数据
│   └── reports/             # 对比报告
├── tests/
│   ├── compiler/            # 按错误码组织的正反例
│   ├── layout/              # 布局快照与属性测试
│   ├── runtime/
│   ├── protocol/            # 协议 schema 与往返测试
│   └── security/            # 权限、ABI、插件隔离测试
└── spikes/                  # 技术验证原型（UI Spike，见 技术验证阶段.md）
```

说明：

- 目录名与 crate 名的对应关系必须一致；新增 crate 必须在本文档中登记。
- `spikes/` 中的代码是**一次性验证代码**，不得被 `crates/` 依赖。验证通过后，有价值的部分必须按本规范重写进入 `crates/`。
- `website/` 与可视化 `studio/` 不在 V0.1 创建。

### 1.2 依赖方向

依赖只能按以下方向流动，由 CI 的依赖检查（`cargo-deny` 的 `bans` 规则或等价脚本）强制执行：

```
aster-cli ──► aster-protocol ──► aster-sema ──► aster-syntax
                    │                 │
                    ▼                 ▼
               aster-ir ◄──── aster-diag
                    │
                    ▼
              aster-layout ──► aster-render-ir
                                     ▲
                                     │
aster-runtime ──► aster-platform     │
        │                             │
        └──────────► aster-backend-* ─┘
```

硬性规则：

1. **UI 语义层不依赖后端。** `aster-ir`、`aster-layout` 不得依赖 `aster-backend-*` 或 `aster-platform`。这是 02 §11.5 的强制要求。
2. **编译器不依赖运行时与平台。** `aster-syntax`、`aster-sema` 不得依赖 `aster-runtime` 或 `aster-platform`。
3. **只有 `aster-platform` 与 `aster-backend-*` 可以包含平台相关代码。**
4. 循环依赖一律禁止。

## 2. 语言与工具链版本

- 工具链使用 Rust，版本由 `aster.toml` 中的 `toolchain` 字段与 `rust-toolchain.toml` 固定。
- 升级 Rust 版本是独立的变更，必须单独提交，并说明原因。
- 语言版本（Aster 的 `language` 字段）与工具链版本分别记录，不相互替代（见 01 §15）。

## 3. 代码规范

### 3.0 语言政策（强制）

以下内容**只允许使用英语**，不得出现中文字符：

- 源代码中的注释（`//`、`///`、`/* */`、`#` 等）；
- 标识符、文件名、模块名、目录名（包括 Aster 源码与 Rust 源码）；
- 编译器、运行时、工具链的诊断源文本（码表中的英语模板、`message`、`suggestions` 等）；译文属于语言包，见 §3.0 第 3 条；
- 错误码表中的消息模板与说明；
- 日志、panic 信息、断言信息、调试输出；
- 测试名、测试中的断言描述、测试夹具中的字符串；
- 协议字段名与枚举值；
- 提交信息（commit message）、PR 标题与正文、代码审查评论。

规则与例外：

1. 字符串字面量中的**测试数据**可以包含中文，但必须位于测试目录中，并在测试名或注释中说明其用途（英文）。这是为了验证中文输入与字体回退（02 §9）。
2. Aster 应用的界面文本属于应用内容，不属于编译器与工具链，不受本条约束。标准库组件的界面文字必须使用消息键，源文本为英语，译文位于语言包中（02 §9.1）。
3. 语言包（`locales/*.toml`）与工具链的译文包是**数据文件**，可以包含任何语言。它们位于 `locales/` 或 `i18n/` 目录下，不受中文字符检查限制。
4. 中文字符的检查由 CI 执行（脚本扫描代码与诊断码表）。发现中文字符时，CI 失败；测试数据例外需在白名单中登记。
5. 本条约束只适用于语言开发相关的代码与产物。

**文档语言：**

- 内部设计文档（`docs/规范/`、`docs/adr/`、`docs/rfcs/`、`docs/设计原始文档/`）可以使用中文，作为项目内部的设计记录。
- 面向外部发布的文档（发布规范、语言参考、用户手册、README、CONTRIBUTING、SECURITY、CHANGELOG 等）必须提供中英双语版本。双语版本的组织方式见 §3.0.1。
- 其他文档默认使用英语。

#### 3.0.1 双语文档的组织方式

- 英语为主文件，中文为对应文件，文件名后缀分别为 `.en.md` 与 `.zh.md`（如 `language-reference.en.md`、`language-reference.zh.md`）。
- 两个版本的结构、标题与代码示例必须一致。修改一方时必须同时修改另一方，CI 检查标题数量与结构的一致性。
- 错误码、命令名、协议字段名在双语版本中保持英文原样。

### 3.1 Rust

- 格式：`cargo fmt --check` 必须通过，使用默认配置，不增加自定义规则。
- Lint：`cargo clippy --all-targets -- -D warnings` 必须通过。例外必须使用带理由的 `#[allow(...)]`，并附注释说明原因。
- 禁止 `unwrap()`、`expect()` 出现在 `crates/` 的非测试代码中，除非有 `// INVARIANT:` 注释说明不变式。
- 错误类型使用 `thiserror` 或等价方式定义，编译器内部错误必须映射到 `E9xxx`。
- 公共 API 必须有文档注释（`///`）。
- `unsafe` 只允许出现在 `aster-platform`、`aster-backend-*`，且每处必须有 `// SAFETY:` 注释说明前提条件。

### 3.2 Aster 源码（`std/`、`examples/`）

- 由 `aster fmt` 统一格式化，不允许手工风格。
- 每个公共符号必须有 `///` 文档注释。
- 每个示例必须可以通过 `aster check` 与 `aster test`。

### 3.3 文件与模块

- 单文件职责单一。超过约 800 行的文件应当拆分（这一阈值是经验值，不是硬限制，评审时判断）。
- 公共接口与实现分离。新增公共接口必须有对应测试。
- 不提交生成的二进制文件、构建产物与本地配置（`target/`、`.DS_Store` 等由 `.gitignore` 排除）。

### 3.4 错误码

- 新增错误码必须同时更新码表（机器可读 JSON）、规范文档（01 §16 或 02 §13）以及至少一个反例测试。
- 码表的一致性由 CI 检查：每个码都有测试，每个测试引用的码都在码表中。

## 4. 分支与提交

### 4.1 分支

- 主分支为 `main`，始终保持可构建、测试通过。
- 功能分支从 `main` 派生，命名为 `feat/<简述>`、`fix/<简述>`、`docs/<简述>`、`spike/<简述>`。
- 分支寿命尽量短。长期分支只用于 RFC 与 Spike，且不得合并未评审的代码。

### 4.2 提交信息

采用 Conventional Commits：

```
feat(layout): support weighted fill in Column

Distribute remaining space by weight; min constraints take priority over weight.
Tests: tests/layout/column_fill.rs
```

- 类型：`feat`、`fix`、`docs`、`refactor`、`test`、`perf`、`build`、`ci`、`chore`。
- 标题不超过 72 个字符。正文说明"为什么"，不重复"做了什么"。
- 由 AI 生成或大幅辅助的提交，必须添加 trailer：`AI-assisted: <工具名>`。这一标记用于审查时加强检查，不改变对代码质量的要求。

## 5. 评审与合并

### 5.1 通用规则

1. 所有变更通过 PR 合并，不允许直接推送到 `main`。
2. 至少一名非作者维护者批准。
3. CI 全部通过：格式、Clippy、测试、依赖检查、许可证检查、错误码一致性检查、布局快照、中文字符检查（§3.0）。
4. 新功能必须附带测试。没有测试的核心功能不允许合并（设计讨论硬规则 3）。
5. 先修复失败的测试，再引入新功能（硬规则 4）。

### 5.2 AI 生成代码

AI 生成的代码不自动视为正确（基础设计文档原则 6）。额外要求：

- 维护者不得未经审查把 AI 生成的代码合并到核心分支（`crates/aster-sema`、`aster-layout`、`aster-runtime`、`aster-platform` 为核心）。
- AI 不得修改验收标准：测试期望值、布局快照、性能阈值的修改必须单独 PR，并说明理由，由维护者审批（硬规则 5）。
- 审查者应检查：是否引入了未声明的依赖、是否绕过类型或权限检查、是否有 `unwrap()` 或 `unsafe` 的滥用、测试是否真的断言了行为（而不是只断言"不报错"）。

### 5.3 CODEOWNERS

| 路径 | 责任人角色 |
|---|---|
| `docs/规范/01-*`、`crates/aster-syntax`、`crates/aster-sema` | 语言负责人 |
| `crates/aster-ir`、`crates/aster-layout`、`docs/规范/02-*` | UI 负责人 |
| `crates/aster-runtime`、`crates/aster-platform` | 运行时负责人 |
| `docs/规范/04-*`、`tests/security` | 安全负责人 |
| `docs/规范/05-*`、`benchmarks/` | 基准负责人 |
| `docs/规范/03-*`、`crates/aster-protocol`、`crates/aster-diag` | 工具负责人 |

一人可以担任多个角色，但**核心路径的评审必须至少由两人完成**，以避免"只有一个人知道如何修改"（基础设计文档 §9，设计讨论 开源治理）。

## 6. 决策流程

| 类型 | 流程 |
|---|---|
| 语言语法、公共 API、协议格式变更 | RFC（`docs/rfcs/`），公开讨论，维护者决定 |
| 架构决策、技术选型 | ADR（`docs/adr/`），记录背景、备选、理由、修改条件 |
| 规范的小修订（不改变语义） | 普通 PR |
| 验收标准与性能阈值修改 | 单独 PR，说明理由，维护者审批 |

### 6.1 RFC 模板

```
# RFC-NNNN：标题
- 状态：提议 / 讨论 / 接受 / 拒绝 / 撤回
- 作者：
- 背景与问题
- 设计（含语法示例与语义）
- 备选方案
- 兼容性与迁移
- 测试计划
- 未决问题
```

### 6.2 ADR 模板

```
# ADR-NNN：标题
- 状态：提议 / 已确定 / 待验证 / 已取代（指向新 ADR）
- 背景
- 备选方案及优缺点
- 决策
- 理由
- 后果与影响范围
- 修改条件（什么情况下应重新评估）
- 关联实验（如 EXP-001）
```

现有 ADR-001 至 ADR-012 位于 `docs/设计原始文档/ASTER-ARCH-001` 中，迁移到 `docs/adr/` 时保留原编号。

## 7. 测试

| 类型 | 位置 | 要求 |
|---|---|---|
| 单元测试 | 各 crate 内 | 覆盖纯逻辑 |
| 语法/类型的正反例 | `tests/compiler/` | 每个错误码至少一个反例，检查码与源位置 |
| 布局快照 | `tests/layout/` | 指定窗口尺寸、DPI、字体下的期望矩形；快照更新需人工审查 |
| 协议 | `tests/protocol/` | JSON schema 校验、往返测试 |
| 安全 | `tests/security/` | 权限拒绝、哈希不匹配、ABI 不匹配、插件崩溃隔离 |
| 性能 | `benchmarks/` | 与 05 文档一致，CI 只做相对回归检查 |

测试命名：`<被测对象>_<条件>_<期望>`，例如 `column_fill_respects_min_width`。

## 8. 许可证与发布

### 8.1 许可证

- 核心代码（编译器、运行时、标准库、工具）建议采用 **Apache-2.0**，原因见 设计讨论"开源许可证怎么选"：包含明确的专利授权条款。
- MIT 为备选，由项目维护者在首次发布前决定。
- 字体、图标、主题素材、示例数据等资源**逐项**记录许可证，存放于 `assets/` 下并附 `LICENSE-ASSETS.md`，不得默认继承源码许可证。
- 第三方代码的许可证必须在 `NOTICE` 或 `cargo-deny` 配置中登记。

### 8.2 贡献者协议

- 建议采用 **DCO**（Developer Certificate of Origin）：提交时使用 `git commit -s` 添加 `Signed-off-by`。
- 是否需要 CLA 由维护者在发布前决定（待定）。

### 8.3 发布

- 版本号遵循语义化版本，V0.x 阶段允许破坏性变更，但必须写入 `CHANGELOG.md`。
- 每个发布版本附带：工具链版本、语言版本、锁定的依赖列表、基准数据（若有）。
- 发布产物签名规则见 04 §8。

## 9. 本地开发

V0.1 的开发环境要求（具体版本号在首次搭建时写入 `aster.toml`）：

- 固定版本的 Rust 工具链（`rust-toolchain.toml`）；
- `cargo-deny`、`cargo-audit`（依赖与漏洞检查）；
- 目标平台的原生开发工具（macOS：Xcode Command Line Tools；Windows：MSVC；Linux：常规 C/C++ 工具链与窗口系统开发包）。

提交前建议运行：

```
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
```

CI 运行的检查项目以仓库中的 `.github/workflows/` 为准。本文件不重复列出实现细节。

## 10. 行为准则与安全报告

- 参与者应尊重他人，对技术观点进行讨论时以证据为准。
- 安全问题不得公开提交 issue，按 `SECURITY.md` 报告。
- 违反行为准则的处理由维护者决定，记录在 `GOVERNANCE.md`。

## 11. 验收

本文件对应的可验证条件：

1. 目录结构与 §1.1 一致，空目录不存在于仓库中；
2. 依赖方向检查在 CI 中运行，违反时失败；
3. 格式、Clippy、测试在 CI 中强制执行；
4. 核心路径有 CODEOWNERS 且至少两人评审；
5. 错误码一致性检查在 CI 中运行；
6. `docs/adr/` 中保留 ADR-001 至 ADR-012 的原编号。
