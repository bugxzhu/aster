# Aster 安全模型、插件机制与包管理规范

**文档编号：** ASTER-SEC-001
**版本：** V0.1 Draft
**状态：** 草案。隔离插件的具体沙箱方案待 EXP-007 验证（Q-05）。
**依赖：** ASTER-ARCH-001（ADR-011）、基础设计文档原则 5、01 语言规范

---

## 1. 范围与原则

本规范定义：

1. 应用的权限模型与默认权限；
2. 三类扩展机制及其信任边界；
3. 包清单、锁文件、依赖来源与完整性校验；
4. 许可证与已知漏洞检查；
5. 发布签名与可复现构建的要求。

本规范遵循基础设计文档原则 5："安全不能依赖开发者自觉，应由工具链、权限模型和发布流程强制落实。"

**关键前提：** 同进程的原生代码（包括 Aster 编译产物与原生扩展）不能被视为安全沙箱。任何需要对不可信代码施加限制的场景，必须使用进程隔离或操作系统级机制。

## 2. 权限模型

### 2.1 权限分类

| 权限 | 示例 API | 默认 |
|---|---|---|
| `fs.read` | `filesystem.read_text` | 拒绝 |
| `fs.write` | `filesystem.write_text` | 拒绝 |
| `fs.read_outside_project` | 读取用户目录 | 拒绝 |
| `net.connect` | `network` 模块（后续版本） | 拒绝 |
| `process.spawn` | `process` 模块（后续版本） | 拒绝 |
| `clipboard.read` / `clipboard.write` | 剪贴板 | 拒绝（用户主动的粘贴与复制由宿主控件直接处理，不经过此权限） |
| `system.notify` | 通知 | 拒绝 |
| `system.tray` | 系统托盘 | 拒绝 |

规则：

1. **默认无权限。** 新应用不能读写文件、访问网络或启动子进程。
2. **权限在清单中声明**（§5），应用启动时由运行时检查。未声明的权限调用在编译期报告 `E5001`，若通过动态方式绕过（如原生扩展），由 §4 的机制兜底。
3. **权限是能力，不是角色。** 权限绑定到具体 API，不绑定到模块或包。
4. **依赖继承权限的限制。** 第三方包声明的权限必须由应用清单显式授予（`grants`）。包不能自行扩大权限。
5. **路径类权限必须限定范围。** `fs.read` 可以声明为作用于特定目录（如 `scope = "$DOCUMENTS/aster"`），编译器对字面量路径做静态检查，运行时对动态路径做规范化后检查。

### 2.2 权限声明示例

```toml
[permissions]
fs.read = { scope = "$PROJECT/data" }
fs.write = { scope = "$APP_DATA" }
clipboard.write = true
```

### 2.3 权限的审计

- `aster permissions` 列出应用及全部依赖请求的权限，并标明来源包。
- 权限变更（新增或扩大）会使锁文件的权限哈希变化，CI 必须要求人工确认。

## 3. 三类扩展机制

ADR-011 确定了三类扩展。它们的信任级别、性能和升级方式不同，不得混用。

| 类别 | 机制 | 信任级别 | 典型用途 | 失败影响 |
|---|---|---|---|---|
| **A. 编译期库** | Aster 源码包，编译时链接 | 与应用同信任域，但受权限限制 | 算法、数据模型、组件、工具函数 | 编译失败 |
| **B. 原生扩展** | 稳定 C ABI 动态库，同进程加载 | 完全信任，等同于应用本身 | 图像处理、专业计算、系统互操作 | 进程崩溃 |
| **C. 隔离插件** | 独立进程，通过 IPC 通信，受 OS 权限约束 | 不信任，默认受限 | 第三方插件、自动化工具、外部服务 | 插件进程退出，宿主继续运行 |

### 3.1 A 类：编译期库

- 以源码形式发布，编译器与应用一起构建。
- 可以调用的权限受应用清单限制。
- 不得包含未声明的原生代码（`unsafe` 或 FFI 块）。若需要，必须改为 B 类。
- 版本冲突（同一依赖的两个版本）在解析阶段报错，不做运行时选择。

### 3.2 B 类：原生扩展

- **ABI 稳定性：** 只允许 C ABI，参数与返回值限于 POD 类型、指针与长度对、不透明句柄。禁止跨边界传递 Aster 的 `List`、`Map`、`String` 等运行时对象，必须通过显式的序列化或句柄接口。
- **版本协商：** 扩展导出 `aster_ext_abi_version()`，宿主在加载时比对；不匹配则拒绝加载（不尝试兼容）。
- **信任声明：** 清单中必须标注 `trust = "native"`，并且应用需要显式接受（`grants.native = true`）。
- **限制：** 不能被当作沙箱。它可以访问宿主内存。安全审查必须按"与应用同等权限"进行。

### 3.3 C 类：隔离插件

- 插件运行在独立进程中，宿主与插件通过带消息格式的 IPC 通信（协议 §3.3.1）。
- 插件的操作系统权限：
  - 默认以普通用户权限运行，不继承宿主的全部权限；
  - 文件访问通过宿主代理（宿主按插件声明的 scope 检查后执行）；
  - 网络与进程创建默认禁止，由宿主代理。
- **崩溃隔离：** 插件异常退出时，宿主收到通知并可选择重启，宿主状态不受影响。
- **资源限制：** 内存与 CPU 上限可在清单中声明；超限时插件被终止。

#### 3.3.1 IPC 协议要求

- 消息格式：长度前缀 + JSON（V0.1）；二进制格式作为后续优化。
- 所有消息必须有 `type`、`id`、`version` 字段。
- 宿主必须校验消息大小上限（默认 4 MB）与字段类型，拒绝格式不正确的消息。
- 插件无法直接调用宿主内部函数，只能调用宿主声明在协议中的方法。

### 3.4 OS 级隔离的局限

本节是 Q-05 的待验证内容。目前已知：

- Linux、macOS、Windows 的沙箱能力差异很大（如 seccomp、App Sandbox、AppContainer 的配置与限制不同）。
- 进程隔离能阻止插件崩溃影响宿主，但不能自动阻止插件读取其自身有权访问的文件。
- **V0.1 承诺的是**：插件崩溃隔离、宿主代理的权限检查、以及文档化的平台差异。**V0.1 不承诺**跨三平台完全一致的系统调用级沙箱。

EXP-007 完成后，必须记录哪些故障能被隔离、哪些能力必须由操作系统或可信沙箱提供。

## 4. FFI 与 unsafe

- V0.1 语言不提供通用的 FFI 语法（01 §18）。
- 原生代码只能通过 B 类扩展接入。应用源码中不允许 `unsafe` 块。
- 标准库中的平台适配层可以使用 `unsafe`，但必须：
  1. 位于 `runtime/platform/` 等固定目录；
  2. 每处 `unsafe` 附带理由注释；
  3. 由审查者逐行审查（见 06 文档）；
  4. 有对应的单元测试或模糊测试。

## 5. 清单与锁文件

### 5.1 `aster.toml`（清单）

```toml
[package]
name = "file-desk"
version = "0.1.0"
language = "0.1"
app = "FileDesk"

[dependencies]
ui-kit = { version = "1.2.0", source = "registry" }
image-core = { version = "0.4.1", source = "registry", trust = "native" }

[i18n]
default_locale = "en"
supported = ["en", "zh-CN"]

[permissions]
fs.read = { scope = "$PROJECT/data" }

[grants]
native = ["image-core"]
```

- `language` 指定语言版本，编译器版本不兼容时拒绝构建。
- `source` 取值：`registry`（官方仓库）、`git`（需写明 `rev` 哈希）、`path`（本地路径，仅用于开发）。
- 发布版本不得包含 `path` 依赖。

### 5.2 `aster.lock`（锁文件）

- 记录每个依赖的精确版本、来源 URL、内容哈希（SHA-256）、许可证标识（SPDX）、声明的权限哈希。
- 锁文件必须提交到版本控制（对于应用项目）。
- 构建时若锁文件与清单不一致，默认失败；`--update` 需要显式执行。

## 6. 依赖来源与完整性

- 每个依赖包必须有内容哈希，构建时验证。哈希不匹配则拒绝使用，并报告 `E5010`。
- 仓库中的包必须带有发布者签名。签名验证失败则拒绝安装。
- 包的源码树必须可以在不联网的情况下从锁文件复现（离线缓存）。
- 不允许安装脚本（build script 或 postinstall）在包安装阶段执行任意代码。若构建需要生成代码，必须通过声明式的构建步骤，并在沙箱中执行（V0.1 中仅允许纯声明式步骤）。

## 7. 许可证与漏洞检查

### 7.1 许可证

- 每个包必须声明 SPDX 许可证表达式。缺失则拒绝发布到官方仓库。
- 项目可以配置允许列表（默认：MIT、Apache-2.0、BSD-2/3-Clause、ISC、MPL-2.0）。
- 不在允许列表中的许可证产生错误，需要显式豁免并记录理由。
- 字体、图标、主题素材等资源必须单独声明许可证，不得默认继承包的源码许可证（见设计讨论）。

### 7.2 漏洞

- `aster audit` 对照已知漏洞数据库检查锁文件中的所有依赖。
- 发现严重漏洞时，CI 失败。
- 数据库的来源与更新方式在 V0.1 之前确定（待定）。

### 7.3 检查的执行时机

| 时机 | 许可证 | 漏洞 | 哈希与签名 |
|---|---|---|---|
| 添加依赖 | 是 | 是 | 是 |
| 每次构建 | 锁文件变化时 | 否 | 是 |
| 发布前 | 是 | 是 | 是 |
| 定期（CI） | 是 | 是 | 否 |

## 8. 发布与可复现构建

- 发行构建使用固定的工具链版本（由锁文件或 `toolchain` 字段声明）。
- 构建输出记录：工具链版本、依赖哈希、编译参数、构建时间（可选固定为 `SOURCE_DATE_EPOCH`）、目标平台。
- 同一输入在同一平台上两次构建的产物哈希必须一致。跨平台不要求一致。
- 发布产物必须签名。签名密钥由项目维护者管理，不存放在仓库中。
- 构建过程中不得使用网络获取未锁定的内容。

## 9. AI 工具与权限

- AI 工具不能修改 `aster.toml` 的 `[permissions]`、`[grants]` 与 `aster.lock`（见 03 §6.4）。
- AI 工具添加依赖时，必须生成建议的权限与许可证信息，由人类确认后才写入。
- `aster run` 需要用户明确授权才能启动应用；授权范围限定在本次会话。

## 10. 威胁模型（V0.1）

| 威胁 | 缓解 |
|---|---|
| 恶意依赖请求超出必要的权限 | 默认拒绝；`grants` 需要人工确认；`aster permissions` 审计 |
| 依赖被替换（供应链攻击） | 内容哈希与签名验证；锁文件 |
| 原生扩展破坏内存 | 只允许 B 类扩展在显式授权后加载；审查与测试；不视为沙箱 |
| 隔离插件滥用系统资源 | 进程隔离、资源上限、宿主代理文件与网络 |
| AI 工具扩大权限或修改验收标准 | 补丁范围限制；快照只能人工更新 |
| 诊断包泄露隐私 | 导出前确认；脱敏选项 |
| 过时依赖含已知漏洞 | `aster audit`；CI 检查 |

未覆盖的威胁（V0.1 不承诺）：

- 对抗具有操作系统最高权限的攻击者；
- 侧信道攻击；
- 用户主动授予过大权限后的数据泄露。

## 11. 漏洞披露

- 安全问题通过 `SECURITY.md` 中列出的私密渠道报告，不得公开提交 issue。
- 项目维护者在确认后，按严重程度公开修复与影响范围。
- 每个安全修复必须附带回归测试（见 06 文档）。

## 12. 验收

1. 未声明权限的文件、网络、进程调用在编译或运行时被拒绝，且有测试覆盖。
2. 篡改依赖内容后，构建被拒绝并报告 `E5010`。
3. 原生扩展 ABI 版本不匹配时拒绝加载，且有测试。
4. 隔离插件崩溃时，宿主进程继续运行，且有测试（EXP-007）。
5. 同一锁文件与工具链在同一平台上两次构建的产物哈希一致。

## 13. 未纳入 V0.1 的内容

- 完整的沙箱实现（三平台）。
- 插件市场与审核流程。
- 自动化的依赖升级机器人。
- 远程插件与远程代码加载。
- 运行时的细粒度资源计量。
