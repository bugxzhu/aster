## 1. 目的

本文是 Aster 第一批设计文档的入口，列出每份交付物的范围、状态、依赖关系，并汇总已经做出的关键决策与仍待验证的问题。

本目录中的规范只定义 V0.1 的最小可靠能力。凡标注"待验证"或"后续版本"的内容，不得被实现为承诺。

## 6. 与原始文档的冲突处理

原始文档之间存在以下不一致，本套规范按如下方式处理：

1. **先设计还是先实现。** 基础设计文档要求完成设计文档后再编码；技术验证阶段文档建议先做 UI Spike。处理：本套规范作为门禁的第一部分；Spike（EXP-001/003）作为进入编译器原型前的必经门禁，二者都要求完成，顺序见 07 文档。
2. **V0.1 范围。** 设计讨论称 V0.1 要能运行文件管理工具，并包含编译器；技术验证阶段要求先不写完整编译器。处理：V0.1 语言规范只覆盖 07 文档定义的子集，不以完整文件管理器为语言规范的验收条件。
3. **渲染是否自研。** ADR-007 与设计讨论希望自研渲染，技术验证阶段原型 B 仍通过 Slint 渲染。处理：V0.1 只自研 UI 语义与布局检查，渲染层保持抽象接口，允许 Slint 作为临时后端。
4. **后端选择。** 设计讨论写"基于 LLVM"，ADR-003 写"待实验比较"。处理：以 ADR-003 为准。
5. **性能数字。** 多份文档给出 5 MB、30 MB、300 ms 等目标。处理：仅作为探索目标，见 05 文档。
6. **仓库结构。** 设计讨论中的 monorepo 目录树与技术验证阶段的 Spike 目录树不同。处理：Spike 使用独立目录；正式仓库结构见 06 文档，只创建正在开发的模块。

## 7. 本套文档的使用规则

- 每份规范顶部标注状态。只有"冻结"状态的内容可以作为实现依据。
- 修改已冻结的内容必须通过 ADR 或 RFC，说明理由、影响范围与迁移方案。
- 规范中的示例代码仅用于说明语法意图；未列入 V0.1 语法的写法一律视为无效。
- 任何规范与实现不一致时，以规范为准修改实现；如认为规范有误，先提出修订，不得直接在实现中偏离。
