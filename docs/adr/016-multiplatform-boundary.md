# ADR-016：多平台目标与平台适配边界

- 状态：已确定（架构约束）；目标平台的实际支持范围待各平台验证后确认
- 日期：2026-10-25
- 来源：架构规划修订，扩展 ADR-012（跨平台策略）与 ADR-014（工具链与目标平台范围）

## 背景

ADR-012 把跨平台目标定义为 Windows、macOS、Linux。随着语言定位转向 AI 原生的原生应用开发，移动端（Android、iOS）也属于目标。如果现在不划清边界，桌面专属的窗口、菜单、文件对话框或快捷键 API 会逐步进入共享的 UI 模型，之后再拆分代价很高。

本 ADR 不改变当前工作的优先级：P0 与桌面端 G0 仍然是下一步。它只增加一项明确的架构约束，并规定移动端的验证顺序。

## 目标平台

| 平台 | 状态 | 说明 |
|---|---|---|
| Windows | 目标 | 桌面，G0 之后验证 |
| macOS | 目标 | 桌面，当前开发与测试平台（ADR-014） |
| Linux | 目标 | 桌面，G0 之后验证 |
| Android | 目标 | 移动，首个移动端验证对象 |
| iOS | 目标 | 移动，在 Android 原型之后验证 |

## 共享内容与可变内容

| 类别 | 归属 | 说明 |
|---|---|---|
| 语言、类型系统、编译器前端 | 共享 | 不因平台而分叉 |
| UI 语义（组件、布局、状态绑定、事件） | 共享 | `aster-ui-model` 与 `file-manager-core` 所代表的层 |
| 业务逻辑 | 共享 | 不依赖任何平台 API |
| 结构化诊断协议（03） | 共享 | 与平台无关 |
| 渲染后端 | 可变 | 按平台或按引擎实现（例如 Slint 适配层） |
| 窗口与应用生命周期 | 可变 | 桌面窗口、移动端的 Activity、Scene 等由平台适配层处理 |
| 输入事件（鼠标、触摸、键盘、输入法） | 可变 | 统一为共享事件模型，平台差异在适配层转换 |
| 系统 API（文件对话框、菜单、托盘、剪贴板、通知、权限） | 可变 | 通过平台适配接口访问，平台不可用时返回明确错误 |

## 设计要求

1. **桌面专属 API 不得无条件进入共享 UI 模型。** 窗口菜单、系统托盘、多窗口、原生文件对话框、快捷键等概念只能出现在平台适配层或带有能力声明的可选模块中。共享模型只能依赖能力（capability），不能依赖具体平台。
2. **能力声明。** 每个平台后端必须声明其支持的能力集合（例如 `multi_window`、`native_file_dialog`、`system_tray`）。共享模型中使用了某项能力时，编译器或校验器必须检查目标平台是否支持，不支持时产生诊断，而不是在运行时静默失败。
3. **依赖方向。** 平台适配 crate 只能依赖共享层，共享层不得依赖任何平台适配 crate。这一规则扩展 06 §1.2 的分层检查，由 `xtask check-layering` 强制执行。
4. **输入与布局单位。** 共享模型使用逻辑单位（dp）和统一的指针与触摸事件抽象。桌面的鼠标悬停与移动端的触摸反馈差异由适配层与组件状态处理。
5. **生命周期。** 共享 UI 模型不假设窗口常驻。移动端的后台、暂停、恢复必须由平台适配层转换为共享的生命周期事件。

## 验证策略

验证顺序固定，不跳过：

1. **桌面端 G0**（当前工作）：完成 Spike 与 G0 的全部条件，包括远程 CI 与人工检查。
2. **Android 最小原型**：用同一份共享 UI 模型和业务核心，构建一个最小应用（计数器或文件管理器的子集）。验证项目包括：构建产物、在模拟器或真机上运行、触摸输入、生命周期、与桌面版相同的布局检查结果。
3. **iOS 构建与运行**：在 Android 原型的边界经验基础上，验证 iOS 的构建与运行。iOS 构建需要完整的 Xcode 和签名环境，当前开发机只有 Command Line Tools，因此该步骤在环境满足之前不开始。

每一步的结果写入 `benchmarks/results/` 或 `docs/计划/`，未验证的平台保持"未验证"状态。

### 当前环境（2026-10-25）

- 完整 Xcode：未安装（只有 Command Line Tools）。iOS 构建不可执行。
- Android SDK 与 NDK：未安装（`ANDROID_HOME` 未设置）。Android 构建不可执行。
- Java：11.0.2。Android 工具链通常需要更新的 JDK，具体版本在安装 SDK 时确认。
- Rust 目标：仅安装了 `x86_64-apple-darwin`。Android 与 iOS 目标需要单独安装。

## 不做的承诺

在实际验证之前，本项目**不承诺**以下内容：

- 所有组件都能在所有平台上无差别运行。
- 第三方扩展（B 类原生扩展、C 类隔离插件）在移动端可用。
- 所有系统 API 在各平台上可用或行为一致。
- 移动端的性能、体积或启动时间达到任何探索目标。
- 移动端的最低系统版本。

这些内容在对应平台的原型验证之后，逐项记录能力声明与已知限制。

## 与现有决策的关系

- ADR-012：跨平台策略不变；目标平台范围由本 ADR 扩展。
- ADR-014：工具链基线与最终应用最低版本的决定不变；移动端的最低版本单独确定。
- ADR-007（渲染后端）：渲染后端的候选需要在移动端验证，包括 Slint 的移动端支持和许可证条件（见 ADR-015）。

## 后果与影响范围

- P0 工作保持不变，不需要返工。
- 02 规范的 §11.5 增加平台能力声明的要求。
- 07 规划中，G0 之后增加 Android 原型与 iOS 验证两个里程碑。
- `xtask check-layering` 需要在平台适配 crate 出现后增加对应规则（当前仓库中尚无平台适配 crate）。

## 修改条件

- Android 原型完成后，若发现共享 UI 模型必须引入平台相关概念，必须修订本 ADR 并记录理由，而不是在共享层中直接加入平台判断。
- 若某个目标平台被证明不可行（例如 iOS 的分发限制），更新目标平台表。
