下一步应该进入 Aster 的第一个可运行技术原型，但还不是正式开发完整语言。

我建议先做一个独立的实验项目：Aster UI Spike 01。它的任务不是实现所有架构，而是用最小成本回答一个决定项目成败的问题：

> 我们能不能在不依赖完整浏览器引擎的前提下，构建现代、轻量、跨平台的桌面界面，并让 AI 通过结构化数据准确检查和修改布局？

在这个问题得到验证之前，不建议开始开发完整编译器、几十个 UI 组件或可视化 IDE。

## 一、第一项实现：Aster UI Spike 01

## UI 技术验证原型

建议周期：1–2 周，单人配合 AI 编程

第一优先级

目标： 用一个真实的桌面应用，验证技术路线，而不是只写几份设计文档。

第一版只实现一个小型文件管理器界面，重点验证窗口、布局、主题、状态、诊断与 AI 修改闭环。

本阶段不开发正式 Aster 编译器，不自研完整渲染器，不开发可视化 IDE。

## 二、具体实现什么？

建议使用同一份需求，构建两条技术路径。

### 原型 A：成熟框架基线

使用 Rust + Slint 实现标准桌面界面。

- 窗口与基础控件
- 侧边栏、搜索框和文件列表
- 深色/浅色主题
- 窗口缩放与布局调整
- 基本交互和状态更新

作用： 建立可运行的基准，确认成熟框架已经提供哪些能力。

### 原型 B：Aster 自有 UI 语义

使用 Rust 实现最小的 Aster UI 模型，再通过适配层连接候选 UI 后端。

- 自有组件树与属性模型
- 类型化的布局属性
- 明确的样式和主题规则
- 机器可读的布局检查结果
- AI 可以读取和修改的结构化模型
- 将自有 UI 模型转换为 Slint 原型的能力

作用： 验证 Aster 自己的 UI 语义能否在不绑定 Slint 源语言的情况下工作。

这里有一个重要区别：原型 B 初期仍然使用 Slint 渲染，所以它主要验证语言抽象、结构化 UI 模型和 AI 工具链，不能用来证明自研渲染器的性能优劣。渲染器的比较需要后续单独实验。

界面只需包含五个区域：

1. 左侧导航栏：全部文件、最近使用、收藏夹。
2. 顶部搜索框：搜索文件名称。
3. 文件列表：名称、类型、修改时间。
4. 右侧详情面板：展示选中文件的信息。
5. 顶部工具栏：新建文件夹、刷新、主题切换。

先用模拟数据，不接入真实文件系统。这样能够将 UI 架构问题与文件系统权限、异步 I/O 等问题分开。

## 四、必须完成的 5 个验证实验

| 实验       | 实际操作                     | 通过标准                  |
| -------- | ------------------------ | --------------------- |
| 01：原生运行  | 构建并启动应用                  | 不依赖完整浏览器引擎，能够独立运行     |
| 02：布局验证  | 缩放窗口、改变文字长度              | 能检测溢出、尺寸异常和布局冲突       |
| 03：AI 修改 | 要求 AI 将侧边栏宽度从 240 改为 280 | 修改范围明确，构建成功，界面结果符合要求  |
| 04：自动修复  | 故意制造组件宽度超出父容器的问题         | 工具能返回结构化诊断，AI 修复后测试通过 |
| 05：后端隔离  | 修改 UI 适配层而不修改业务模型        | 能明确哪些代码依赖后端，哪些与后端无关   |

同时记录构建时间、安装包体积、内存占用和启动时间。所有数据都要在相同的操作系统、构建模式和测量条件下采集。

## 六、什么时候才开始写正式语言？

当以下条件成立时，再进入下一阶段：

- 成熟框架基线可以正常运行。
- Aster 自有 UI 模型能够描述同一套界面。
- UI 模型能够输出明确的布局与组件诊断。
- AI 能够通过工具接口完成至少一种修改、检查和修复闭环。
- 已记录 Slint 可以直接满足的需求，以及必须自行实现的部分。

通过后，下一阶段才是 Aster UI IR V0.1 与语言前端原型：确定正式的 AST、类型化属性、组件定义和布局约束，再开始设计 Aster 的实际源代码语法。

我的建议是，现在先实现原型 A 和原型 B，不要继续扩展设计文档。 最重要的第一份代码不是完整编译器，而是能够用数据证明 Aster 自有 UI 模型是否值得继续投入的最小可运行项目。
